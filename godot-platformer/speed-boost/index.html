Notice the pattern: the first two steps are in the editor (clicking and saving), the rest are in the script (typing code). This is how Godot work usually flows — you set up the structure visually first, then teach it behavior with code.

Breaking one big task into smaller pieces like this is called problem decomposition. It's one of the most useful habits in programming. When something feels too big, list the steps until each one feels small.

Our boost coin reaches over and talks to the player directly. That's perfect for a small, focused feature. But as a project grows, you start asking:

"What if the coin needs to update the HUD's score? And play a sound? And trigger an achievement? And let an analytics system know? Should every coin script know about every one of those?"

Godot has a pattern that solves this gracefully: an autoload (singleton) — a special script that's always loaded and reachable by name from anywhere. Many projects make one called Global, GameState, or EventBus. The coin emits "I was collected!" once, and any system that cares can listen — without the coin knowing they exist.

You'll see this pattern crop up a lot. For now, our direct call is the right starting point — it's easier to follow, and the singleton "upgrade" path will make more sense once you've built a few features the simple way first.

Your project already has a Global autoload — peek at it later if you're curious. In Step 7 we'll show what the singleton version of this coin would look like.

# How many seconds the boost lasts

# Runs when something walks into this Area2D
func _on_body_entered(body):
    # Remember the player's normal speed so we can restore it
    var original_speed = body.speed

    set_deferred("monitoring", false)

    await get_tree()._____(boost_duration).timeout
    
    # Boost is over — restore normal speed
    body.speed = original_speed
    
    # Remove the coin from the game
    _____()

About that await

      await is GDScript's way of saying "pause this function here, let the rest of the game keep running, and resume when the timer finishes." Without it, you'd need to count down seconds yourself every frame. create_timer() creates a one-shot timer that fires after the duration, and .timeout is the signal we wait for.
    


    

      
      

        
Godot's editor colors your code as you type. The colors aren't decorative — they tell you something about how the engine reads each word.

        
Purple = reserved keyword. These are words GDScript itself uses, like extends, var, func, if, await, return. You can't use them as variable names. When you see purple, you know "the language itself is doing something here."

        
Orange/yellow = function name. Whether you're calling a function (queue_free()) or defining one (func _on_body_entered():), the function's name is highlighted.

        
Teal/green = type. Like float, Area2D, String. These tell GDScript what kind of value something is.

        
Pink/light purple (@export) = annotation. Annotations modify how the editor or engine treats the next thing — @export exposes a variable to the Inspector; @onready waits to set a variable until the node is ready.

        
If a word you expect to be purple isn't, you probably misspelled it. That's the editor giving you a free spelling check.

      

    


    

      
      

        
GDScript doesn't require any particular order, but there's a strong convention most projects follow. Following it makes your scripts easier for you (and others) to read later:

        

# 1. Class declaration — what kind of script this is
class_name BoostCoin
extends Area2D
 
# 2. Signals this script can fire
signal collected
 
# 3. Exported (Inspector-visible) variables
@export var speed_multiplier: float = 2.0
 
# 4. Other variables (not exposed)
var _has_been_collected = false
 
# 5. _ready and other engine callbacks
func _ready():
    pass
 
# 6. Your custom functions, including signal handlers
func _on_body_entered(body):
    pass
        

        
Following this order means anyone (or future-you) can scroll a script top-to-bottom and see "what is this script for?" → "what can it announce?" → "what knobs does it have?" → "what does it do when things happen?" — in that order. It's a tidy way of telling the story.

      

    


    

      
      

        
Without @export, a variable is just data inside your script. Other scripts can read it; the Inspector cannot.

        
Adding @export tells the editor: "draw a field for this in the Inspector panel." Whenever a node with this script is selected in any scene, the Inspector shows that field, pre-filled with the default value. Designers — including you — can tweak it per-instance without ever touching the script.

        
This is huge for game feel. Want one coin in the level to give a 1.5× boost and another to give a 3× boost? Drop two BoostCoin instances, click each, change Speed Multiplier in the Inspector. No code changes. No new scripts.

        
Godot also supports typed exports like @export var color: Color (Inspector shows a color picker), @export var icon: Texture2D (Inspector shows a file picker), and @export_range(0.0, 10.0) var x: float (Inspector shows a slider).

The completed script

    
Here it is, all blanks filled in, ready to copy into your project:


    

extends Area2D
 
# How much faster the player moves while boosted
@export var speed_multiplier: float = 2.0
 
# How many seconds the boost lasts
@export var boost_duration: float = 4.0
 
func _on_body_entered(body):
    var original_speed = body.speed
    body.speed = original_speed * speed_multiplier
    
    visible = false
    set_deferred("monitoring", false)
    
    await get_tree().create_timer(boost_duration).timeout
    
    body.speed = original_speed
    queue_free()
    


    
Where to go from here


    

      
      

        
The fix is simpler than you'd think: don't save the player's current speed. Instead, the player's script should expose a base_speed variable that never changes — only the live speed changes.

        
In player.gd, add a new variable at the top:

        

var base_speed: float = 500.0  # Never overwritten by boosts
        

        
Then in your coin script, change two lines:

        

# OLD:
var original_speed = body.speed
body.speed = original_speed * speed_multiplier
 
# NEW:
body.speed = body.base_speed * speed_multiplier
 
# And when the boost ends:
body.speed = body.base_speed
        

        
Now no matter how many coins overlap, the player always returns to base_speed — never to a "boosted-mid-collection" speed.

      

    


    

      
      

        
Remember the Side Quest in Step 2? Here's how the "more organized" version looks. The coin doesn't touch the player directly anymore — instead, it shouts to a singleton (your project's global.gd) and lets the player listen.

        
Why bother? Imagine you want five different power-up types, or two players in co-op who both react to one collectible, or other systems (HUD, sound, achievements) that also need to know "a boost just happened." Connecting everything directly gets messy. A singleton stays clean.

        
It looks like this:

        

# In global.gd:
signal boost_started(multiplier: float, duration: float)
 
func start_boost(multiplier, duration):
    boost_started.emit(multiplier, duration)
        

        

# In boost_coin.gd, instead of touching the player:
Global.start_boost(speed_multiplier, boost_duration)
        

        

# In player.gd, listen for the broadcast:
func _ready():
    Global.boost_started.connect(_on_boost_started)
 
func _on_boost_started(multiplier, duration):
    speed = base_speed * multiplier
    await get_tree().create_timer(duration).timeout
    speed = base_speed
        

        
Same effect, more decoupled. Once you've built a few collectibles the direct-call way, the singleton starts to feel like a natural cleanup.
