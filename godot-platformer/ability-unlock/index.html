How to find it yourself

  1. Open player.gd using either method above.
  2. Press Ctrl+F (Cmd+F on Mac) and search for _glide. Press Enter to jump to the next match.
  3. You'll see several matches as you cycle through — the function definition (func _glide()), a sound variable (_glide_sfx), and others. Keep pressing Enter until you land on the line that looks like this:
    # Remove the '#' below to enable the glide special ability #_glide()
  4. Stop when you land on the #_glide() line shown above. That’s where we’re heading. (We’ll do the actual edit in the next step.)
Where this code lives
The four ability switches all sit inside _physics_process — the function that runs every frame to handle the player's per-frame behavior. The line you're looking for is always the same shape: a helpful comment that says "Remove the '#' below to enable…" followed by a #-prefixed function call. That comment is your landmark — it only appears at the four ability switches.
// STEP_03

Now turn the ability on

You’re looking at a line that starts with #:

# Remove the '#' below to enable the glide special ability #_glide()

In GDScript, a line starting with # is a comment — the computer ignores it. Right now there’s a # in front of _glide(), which is why the ability doesn’t work. Remove the # to turn the ability on.

Try it — click the button to remove the #:

GLIDE ABILITY: DISABLED
# Remove the '#' below to enable the glide special ability #_glide()

With the # in front, Godot skips this line entirely. The glide ability never runs.

That’s the whole concept. Only delete the # — leave the spaces in front of it alone, since GDScript uses indentation to keep its structure. Save with Ctrl+S (Cmd+S on Mac).

Now go try it out. Run your game — press F5, or click the ▶ play button in the top-right corner of the Godot editor. When the game starts, jump once, then hold the jump button while you’re still in the air. You should fall slowly with a glide sound — your first unlocked power.

Almost every programming language lets you leave notes in your code that the computer ignores — called comments. Programmers use them to explain what code does, mark things to fix later, or label sections so other people (and their future selves) can understand the file.

In GDScript, a comment starts with #; everything after it on that line is for human eyes only. Comments have a useful side effect: if you put # in front of a line of working code, that whole line becomes a comment too — so it stops running. Programmers call this "commenting out" code. It’s a fast way to disable a line without deleting it — great for testing, experimenting, or hiding features until they’re ready, which is exactly what your game is doing.

The lines you’re unlocking, like _glide(), are called function calls — short instructions that trigger a "recipe" of code defined elsewhere in the script. The # in front of each call disables that trigger. Remove it, and the call runs.

Now unlock the other three

You just learned the workflow. Apply the same skill to the remaining abilities — same pattern, different names. Each lives in the same _physics_process function, each is preceded by a "Remove the '#' below to enable…" comment.

You might have noticed something curious. The Input Map doesn't say "the up arrow makes the player jump." Instead, it says "the up arrow triggers an action called player_1_jump." Why the extra step?

Because that middle step — the named action — gives you flexibility you'd never get otherwise. Click any key below to see what happens:

Three keys all trigger the same player_1_jump action — keyboard, spacebar, gamepad. The code only ever asks "did player_1_jump fire?" It doesn't care which key was pressed. That's why Player 2 can use W while Player 1 uses Up: the code is identical, only the action name differs.

Bottom line: this design lets one piece of code work for any key, any controller, any player. You'll see it everywhere in Godot.

// STEP_05

Three skills you'll likely use again

These aren't tricks specific to glide or phase — they're general concepts that come up in lots of moments while you're modding or designing a game:

  1. The # switches code on and off. Adding it disables a line; removing it enables one. Indentation matters.
  2. The Input Map shows you which inputs do what. Project Settings → Input Map, search and expand.
  3. One change at a time. Edit, save, test, repeat. Always know which change caused which result.
